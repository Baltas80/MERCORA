# MERCORA Onion staging

This is the local/staging deployment path for the MERCORA Onion Service. It is intentionally separate from any production payment infrastructure.

## Requirements

- Docker Engine with Docker Compose v2 for the recommended staging path.
- Tor Browser for the client-side test.
- A strong `POSTGRES_PASSWORD` kept outside Git.

## Recommended start: Docker staging

```bash
export POSTGRES_PASSWORD='use-a-local-secret-not-stored-in-git'
docker compose -f docker-compose.yml -f docker-compose.onion.yml up -d --build
```

The application remains bound to loopback on the host and is reachable by the Tor container only through the private Docker `onion_edge` network. The Tor container has a separate egress network so it can join the Tor network without giving the application direct Internet egress.

The Onion Service container is explicitly configured as a client/Onion-Service process, not a public relay: `ORPort 0`, `DirPort 0`, and `ExitPolicy reject *:*` are enforced in the service configuration and again on the Tor command line. Image defaults are not treated as the effective MERCORA configuration.

## Obtain the Onion address

```bash
docker compose -f docker-compose.yml -f docker-compose.onion.yml exec tor cat /data/mercora/hostname
```

Open the resulting `.onion` address in Tor Browser.

## WSL development path

When Docker is not being used and MERCORA is already running directly on WSL at `127.0.0.1:8080`, use the dedicated launcher:

```bash
bash scripts/start-onion-wsl.sh
```

The launcher:

- verifies that the local application health endpoint responds;
- creates `/var/lib/tor/mercora` with owner `debian-tor` and mode `700`;
- writes an isolated Tor configuration with `SocksPort 0` and `ControlPort 0`;
- validates the Tor configuration before starting it;
- runs Tor as `debian-tor`, avoiding the root/ownership mismatch that occurs when `sudo tor` is used directly;
- uses a v3 Onion Service mapped to `127.0.0.1:8080`.

Leave the launcher terminal running. From another WSL terminal, obtain the generated address with:

```bash
sudo cat /var/lib/tor/mercora/hostname
```

Do not expose or commit `hs_ed25519_secret_key` or any other generated Onion Service private material.

## Verify locally

```bash
curl --fail http://127.0.0.1:8080/api/healthz
docker compose -f docker-compose.yml -f docker-compose.onion.yml exec tor grep -E '^(ORPort|DirPort|ExitPolicy)[[:space:]]+' /data/torrc
docker compose -f docker-compose.yml -f docker-compose.onion.yml exec tor test -s /data/mercora/hostname
```

Expected Tor configuration includes:

```text
ORPort 0
DirPort 0
ExitPolicy reject *:*
```

Expected application response:

```json
{"status":"ok"}
```

## Important security properties

- `SocksPort 0`: no Tor SOCKS proxy is exposed by the service configuration.
- `ControlPort 0`: no Tor control interface is exposed by the service configuration.
- `ORPort 0` and `DirPort 0`: the staging process does not accept public relay or directory traffic.
- `ExitPolicy reject *:*`: the process is not configured as an exit relay.
- The v3 service keys are generated in the local Tor service directory/volume and are never committed to Git.
- The recommended Docker staging path keeps the application behind the private `onion_edge` network rather than exposing it directly to the Internet.
- The application container uses a read-only filesystem, drops Linux capabilities and enables `no-new-privileges`.
- Do not copy `tor_data` or the WSL Onion Service directory into the repository or share the service private key.
- Do not put real funds or production credentials into this staging environment.

## Current limitation

The staging Onion address is generated by the machine that runs the Onion Service. It cannot be known from GitHub before the service is started. The address should therefore be reported only after the running Tor instance exposes its generated `hostname` file.
